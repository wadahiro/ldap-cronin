# Active Directory (a real AD, Samba AD)

The `ad` profile clones and compares Active Directory and Samba4 AD. It is chosen when the root DSE's `supportedCapabilities` contains `1.2.840.113556.1.4.800`; how it differs from the generic profile is in the [table in the README](../README.md#server-types-profiles).
By default every attribute a client can write is copied ([below](#how-it-behaves)); `ldap-cronin list-attrs -profile ad` prints the allow lists of `mode = "allowlist"` (the ones Samba4 has out of the box); `ldap-cronin check -config config.toml` reads the source and the target and says which attributes the entries hold that `clone` leaves behind and why, what the target's schema lacks, and the next steps (`-attrs`: every attribute of every kind).
For a first run, the [tutorial](tutorial-ad.md) goes through a complete configuration and a clone into the lab and
into a test AD.

## Configuration

```toml
[source]
url = "ldaps://src-ad.example.com:636"
bind_dn = "CN=Administrator,CN=Users,DC=ad,DC=example,DC=com"
# ca_file = "ca.pem"                # the CA of a self-signed or internal certificate
[target]
url = "ldaps://dst-ad.example.com:636"   # LDAPS: required to set passwords
bind_dn = "CN=Administrator,CN=Users,DC=ad,DC=example,DC=com"
[scope]
base_dn = "OU=IDM,DC=ad,DC=example,DC=com"   # or the domain root, for the whole domain (built-ins left out),
                                             # or a list of OUs as one scope: ["OU=Tokyo,...", "OU=Osaka,..."],
                                             # or OU=*,DC=... for every OU right under the domain
# [mapping]
# mode = "marker"                   # the default here: clone writes a marker of the source object
# attribute = "adminDisplayName"    # the attribute that holds it
```

[`config.example.toml`](../config.example.toml) has every key. A source and target must both be AD; cloning between an AD and a generic server is not supported.

## How it behaves

- **Users are created in three steps**: add (disabled), set `unicodePwd` with a modify, then set `userAccountControl` to the source's value (without the bits the server manages). A real AD accepts `unicodePwd` only in a modify, never in the add ([KB 269190](https://learn.microsoft.com/en-us/troubleshoot/windows-server/active-directory/change-windows-active-directory-user-password)), and `userAccountControl` comes last because a disabled or never-expires flag changes the preconditions of setting the password. A re-run sets the password only for a user whose creation stopped before it (`pwdLastSet=0`), so it never rolls back a password the program under test changed. A user who must change the password at the next logon on the source (`pwdLastSet=0`) must on the target too: `pwdLastSet` is set to 0 right after the password (a computer's 0 is a password never set, so a computer is left with the one it got). `pwdLastSet` is not compared by `diff`: it holds the time of the clone.
- **Built-in objects are never cloned or rewritten**: everything with `isCriticalSystemObject=TRUE` (Administrator, krbtgt, ...) is excluded, even when `base_dn` is `CN=Users`.
- **Every OU of the domain, without the containers**: `base_dn = "OU=*,DC=ad,DC=example,DC=com"` stands for every OU right under the domain the source holds, as a list of base DNs, but the built-in ones (`OU=Domain Controllers`). `CN=Users`, `CN=Computers`, `CN=System` and what they hold are left out, but for what a reference of the scope names (a member, a manager: cloned as a referenced object, without its own references) and the groups there holding entries of the scope (given those members). `OU=*` may stand only first, under any parent (`OU=*,OU=Branches,DC=...`). The wildcard is resolved when a session opens, against the source or the dump; a dump records the OUs it stood for. Verified on a dump of a Windows Server 2019 domain: the clone of `OU=*` is that of the domain root without `DnsAdmins` and `DnsUpdateProxy`, nothing written under `CN=Users`.
- **The whole domain**: `base_dn` may be the domain root itself. The root entry is the target's own (no kind selects it: its password policy and `gPLink` stay the target's), the built-ins are left out as above, and what is of no kind (`CN=System`, GPOs, DNS records) is counted. The summaries mark the built-ins `(built-in: the target's own)`. A dump of the root holds the domain partition only, as a search of it does on the server; the configuration partition is in its own section. On a new Windows Server 2019 domain, the only entries of a kind that are not built-in are `DnsAdmins` and `DnsUpdateProxy`, which clone then updates. Verified: a whole Windows Server 2019 domain dumped, cloned into a Samba lab, diff clean, a second run writing nothing. Mind the load on a large domain. The one write they get is the membership of entries of the scope (next point).
- **The groups an entry belongs to come along, wherever they are.** A membership is the group's `member` value, so an OU walked alone never carries a user's membership in a group of another OU, or in Domain Admins. clone finds those groups through the entries' back links (`memberOf`, and any other pair the schema links, such as Exchange's `authOrigBL` for a group restricting who may send to it, when the group's allow list names `authOrig`), and gives each the values that name entries of the scope, nothing else of its own:
  - a group outside `base_dn` is created as a referenced entry is (without its own references) and given those members (`[scope] outside_groups = "clone"`, the default; `"existing"` only gives them to a group the target holds; `"skip"` leaves them out);
  - a built-in group (Domain Admins, Account Operators, ...) is the target's own, of the same domain: it is given those members (`[scope] builtin_groups = "add"`, the default; `"skip"` leaves it as it is). On a new test domain this is what production has: the cloned administrators are administrators of the test domain, with the fixed password. Never point it at a domain shared with others.
  - `check` lists them before, the summaries count them (and those left out, with why), `diff` compares their values that name the scope, and a dump carries them with every member. A dump taken before this carries none of them: it says so, dump again. Only groups are followed, one level: a group of another OU is not given its own memberships elsewhere. The settings are independent of `[scope] references`: with `references = "skip"` such a group is still created unless `outside_groups = "skip"`.
- **Kinds.** Users are `(&(objectCategory=person)(objectClass=user))`, which leaves computers and contacts out; groups are `(objectClass=group)`; computers are `(objectCategory=computer)`, which leaves managed service accounts out; contacts are `(objectClass=contact)`. All five kinds (with `ou`) are cloned unless `[scope] objects` lists fewer.
- **Computers are accounts too.** A computer is added as a disabled workstation trust that needs no password (`userAccountControl` 4130), gets the fixed password, and then its source `userAccountControl` (4096 for a workstation), so its account type is the source's from the add on. A joined computer has a password, so the clone has one too; it is not the machine's, so the lab computer cannot log on as the real one. Its LAPS passwords, shadow credentials (`msDS-KeyCredentialLink`) and resource-based delegation are not cloned unless `[attributes] credentials = "copy"` (next point but one); its gMSA password never is. The values the machine refreshes by itself (`msDS-SupportedEncryptionTypes`, `lastLogonTimestamp`) are not in the defaults, so a live source does not differ on every diff.
- **The primary group** (`primaryGroupID`, the RID of a group: Domain Users for a user, Domain Computers for a computer) is the source's when it is another group. A RID is each domain's own, so clone goes through the group's DN: the group (created first when it is outside the scope, as a group holding entries of it is) is given the account as a member, as AD requires, and then `primaryGroupID` is set to its RID on the target, after which the DC drops that member value, as the source's group lacks it. The built-in groups (RID below 1000) are the same in every domain. `diff` compares the group each side names, not the number; a dump carries a primary group outside its base DN. An account whose group cannot be found keeps the default, with a warning and a count.
- **Never cloned**: identifiers and server-managed attributes (`objectGUID`, `objectSid`, `sIDHistory`, `whenCreated`, `uSNChanged`, `memberOf`, `pwdLastSet`, the password hashes, ...). Listing one in `[attributes]` is an error.
- **Credentials the source returns, with `[attributes] credentials = "copy"`.** By default no credential is cloned. With it, those AD returns over LDAP to a reader with the rights and lets a client write are: LAPS (`ms-Mcs-AdmPwd`, `msLAPS-*`), shadow credentials (`msDS-KeyCredentialLink`), resource-based delegation (`msDS-AllowedToActOnBehalfOfOtherIdentity`), `userPassword`, `unixUserPassword`, `userPKCS12`, the credential roaming blobs (`msPKI*`) and `msTPM-OwnerInformation`; by default every attribute a client can write is copied, so they come along where the entries hold them (with allow lists, name them in `extra_include`). It is for a clone that is to hold the structure the source has, one test domain cloned from another, say. What AD never returns stays out (`unicodePwd`, `supplementalCredentials` and the other hashes; the gMSA password, which the DC constructs for each read): the accounts still get the fixed password. A value encrypted to the source domain's key (`msLAPS-EncryptedPassword`) is copied as it is and means something only where the target has the source's domain SID. The delegation, a descriptor whose ACEs name who may act as the account, is written over LDAP with each SID the target's, as `[attributes] acl = "copy"` translates an ACL (next point; with or without that setting): after every object exists, a principal of the source's domain as the target's object at the same DN, an ACE whose trustee the target lacks left out with a warning and counted (if all are, nobody may act as the account), and `diff` compares the result. A dry-run's LDIF carries the source's SIDs and says so. The values are printed nowhere: `check` and the logs name the attributes only, a dry-run's LDIF carries them with `-with-password` only, and `diff` compares them but prints a fingerprint (`(credential, sha256 …)`) instead of a value. From a dump, it needs one taken with `dump -with-credentials` (refused otherwise). A native import (`[target.lab] native = true`) copies them too, and as it keeps the source's domain SID, the delegation and the encrypted LAPS password mean there what they mean on the source. Measured on Samba 4.19.5: over LDAP, `userPKCS12`, `userPassword` (a plain attribute there: the fixed password still logs the user on), `unixUserPassword`, the three `msPKI*` blobs, `msDS-KeyCredentialLink`, `msTPM-OwnerInformation` and the legacy LAPS attributes (the schema the LAPS installer adds, given to both domains) are copied and `diff` finds nothing; natively, `userPKCS12` and the delegation, its SIDs kept. Samba lets only the system write the delegation, so over LDAP into Samba it is left out (What the target refuses, below). Measured from Samba 4.19.5 into Windows Server 2019 (the EC2 lab), over LDAP: every one of those, the legacy LAPS and Windows LAPS attributes (`msLAPS-Password`, `msLAPS-EncryptedPassword`, `msLAPS-PasswordExpirationTime`, their schema given to both domains with the real OIDs) and the delegation, written with the target's SIDs (a group and a computer of the scope as the target's, the built-in Administrators as it is, the domain's Administrator as the target's, a user outside the scope left out), and a second `clone` writes nothing; `userPassword` is a plain attribute there too with the default `dSHeuristics` (the fixed password logs the user on). Windows takes a `msDS-KeyCredentialLink` value of any form from the Administrator (a dummy one was copied). Not verified: `userPassword` with fUserPwdSupport turned on in `dSHeuristics`, where it would set the account's password and replace the fixed one. Not on a generic server: there `userPassword` is the account's password, which the fixed password replaces.
- **ACLs, with `[attributes] acl = "copy"`.** By default each object keeps the ACL the target gives it. With it, every object clone writes (the entries of the scope and those it creates outside it, not the containers above `base_dn`, which are the target's own) gets the source's owner, group, protected flag and explicit ACEs (`nTSecurityDescriptor`, read and written with the SD flags control: no SACL), after every object exists. That carries "Protect object from accidental deletion" (a deny ACE on the object and one on its parent), "User cannot change password", delegations to a group of the scope, and the default ACEs each object was created with. The inherited ACEs are left to the target, which computes them from the object's parents. An object created over LDAP gets the target's own SID, so each SID is translated: a principal of the source's domain is the target's object at the same DN (its `objectSid` read there), a built-in one (a RID below 1000: Domain Admins, the Administrator) the target's of the same RID, and every other SID (Everyone, Authenticated Users, `BUILTIN\...`, a trusted domain's principal) passes as it is. An ACE whose trustee has no principal on the target is left out, with one warning per trustee and a count in the summary: a principal not cloned (outside the scope and named by no reference), or a SID no object of the source has (a deleted principal's; from a dump, also one the dump does not hold). It would grant or deny nobody on the target anyway. `diff` compares what clone writes: each object's owner, group, protected flag and explicit ACEs (not their order), the SIDs translated the same way, and counts the ACEs left out instead of comparing them. A dry-run cannot read the target's SIDs, so its LDIF carries the source's (it says so). Measured on Samba 4.19.5 (two domains of their own SIDs, a deny ACE keeps even the Administrator from deleting the object); on Windows Server the explicit ACEs a client writes are kept and the inherited ones computed the same way (see [DEVELOPMENT.md](DEVELOPMENT.md#research-notes-can-samba-create-objects-with-a-chosen-objectguid--objectsid-measured)); measured into Windows Server 2019 (the EC2 lab) too: the Administrator gives an OU a user of the scope as its owner, an ACE whose trustee is outside the scope is left out, and a second `clone` writes nothing. A native import has `[target.lab] acl` instead, which keeps the SIDs ([lab.md](lab.md)).
- **Every member is reproduced where AD allows it.** A linked attribute such as `member` can only name an object the target holds, so for each value outside the scope clone:
  - clones the object if it is of a kind (a user or group outside `base_dn`), without its own references (`[scope] references = "clone"`, the default);
  - references a built-in the target holds as it is (`Domain Admins` of the same domain), but never creates one;
  - adds a well-known principal (Everyone, Authenticated Users, ...) by SID (`<SID=S-1-5-11>`), so the target's DC creates its own foreign security principal;
    Windows takes one only in a built-in group: into another group (a global one refuses with 53, a domain local one with 80, `0x56C`, by DN or by SID; measured on Windows Server 2019) such a value is skipped with its reason and counted, and `diff` counts it instead of comparing it. Samba takes it in any group, so the case arises when a Samba source holds it;
  - skips anything else with a warning (a principal of a trusted domain, which a test domain does not trust; a built-in the target lacks; an entry of the configuration partition), one per entry it names, and says what it names; the summaries count the values per attribute and reason, and `diff` counts them instead of comparing them.
- **References to entries the source does not return.** AD returns a group's `member` values (and every other reference) whatever the reading account may read of what they name, and removes a value naming a deleted entry, so a value whose entry the source does not return names one that account may not read. clone creates a placeholder there (`[scope] unreadable_refs = "placeholder"`, the default with `references = "clone"`), so the value can be written: a contact (no account, no SID, no logon) named as the value names it, whose `description` begins `ldap-cronin placeholder`, and the parents the source does not return either, as organizational units (`OU=`) or containers (`CN=`). A value naming something else (`OU=`) is skipped with its reason. Each placeholder is a warning, and the summary counts them; `diff` compares the values, and counts the placeholders under `base_dn` instead of reporting them as `ONLY_TARGET`. A placeholder stands only for the value: what it stands for may be a user or a nested group, whose own groups and members are not there. `unreadable_refs = "skip"` leaves such values out, counted with their reason, as for anything else clone cannot write. A dump lists these entries (`# unreadable:`, [the dump](dump.md)).
- **References into the configuration partition.** Exchange attributes such as `showInAddressBook` (the address lists a recipient is shown in) or `homeMDB` (the mailbox database) name entries under `CN=Configuration`, which clone does not create, so their values are skipped by default (or `exclude` them). For a lab, `[scope] configuration_refs = "clone"` creates what they name, and the parents the target lacks, from the source: their object classes, naming attribute and what a client can write on their classes, without what is never cloned and without their own references; they count as referenced objects of the kind `configuration`, and `diff` then compares the values. It needs the target's configuration partition to be the source's (`lab up --config`) and its schema to have the classes: a lab has none of Exchange's (`msExchOrganizationContainer`, `msExchContainer`, ...) until it is made from an image with Exchange's schema (`make image EXCHANGE_ISO=...`) or `ldap-cronin schema` gives them from production, with the `possSuperiors` that let an address list live under them. Until then each entry that cannot be created is one warning with the server's reason. The containers right under `CN=Configuration` (`CN=Services`, `CN=Sites`, ...) are taken to be there, as every forest has them, so a dry-run's LDIF adds only what is below them; nothing is ever created under `CN=Schema` or `CN=Partitions` (a schema change cannot be undone, and the partitions define the lab's forest): such a value is skipped with its reason. `[target.lab] native = true` refuses the setting. Not for a real test domain: Exchange objects there would confuse a later Exchange setup.
- **Every attribute a client can write, by default.** `clone` copies and `diff` compares every attribute the source's schema lets a client write on the class of each kind (`organizationalUnit`, `group`, `user`, `computer`, `contact`): what the class, the classes it derives from and their auxiliary classes may or must contain, without `systemOnly` attributes (but the resource-based delegation, What the target refuses below), constructed ones, back links, what is never cloned (identifiers, credentials) and the marker; `[attributes] exclude` takes more out. So the attributes of products (Exchange's `proxyAddresses`, `extensionAttribute1`-`15`, Entra Connect's `mS-DS-ConsistencyGuid`, ...) and of your own extensions come along without being named. `gPLink` and `gPOptions` of an OU are left out, with why in `check`: they link GPOs, which are not cloned, so they would link the target's OUs to policies it lacks (an allow list may still name them). An attribute the target's schema lacks is left out with a note instead of stopping `clone` (run `ldap-cronin schema` first for your extensions); a dry-run does not read the target, so its LDIF has them all. An auxiliary class attached to single objects (not in the schema) is not followed: name its attributes by switching to the allow lists. Some attributes AD lets a client write still belong to the server in practice (the ones a DC refreshes on its own, such as `msDS-SupportedEncryptionTypes` of a live computer): they are copied once and may differ later; `exclude` them if they get in the way. Values that name the source domain by SID (`msExchMasterAccountSid`, `securityIdentifier`) are copied as they are, so they name the source's principals unless the lab has the source's domain SID (`[target.lab] native = true`); so are the descriptors of products (Exchange's `msExchMailboxSecurityDescriptor`). The resource-based delegation is the exception, translated (credentials, above).
- **The allow lists** (`[attributes] mode = "allowlist"`, `list-attrs -profile ad`) are what Active Directory Users and Computers shows on the property sheets of each kind, as Microsoft [maps them to attributes](https://learn.microsoft.com/windows/win32/ad/mappings-for-the-active-directory-users-and-computers-snap-in) (contacts: a user's General, Address, Telephones and Organization sheets), without what clone never writes (what the server keeps, back links, `primaryGroupID`), and with what the mapping leaves out that production directories use: the employee identifiers IdM products key on (`employeeID`, `employeeNumber`, `employeeType`), the UNIX Attributes sheet (`uidNumber`, `gidNumber`, `loginShell`, `unixHomeDirectory`), `servicePrincipalName` and the Managed By sheet of a computer, a group's `adminDescription` (Entra Connect's default filter), and `displayName`, `middleName`, `division`. `internal/profile/ad.go` marks which is which. Anything else is added with `extra_include`.
- **Attributes of a schema extension** (your own, or a product's; `check -config config.toml` lists the ones your entries hold, and which the target lacks) need their definitions in the target's schema. By default one the target lacks is left out with a note; with the allow lists, once a list names it (`extra_include`, `[attributes.include]`), `clone` compares the two schemas before writing anything and refuses to start, naming each attribute the source defines and the target lacks, and the kinds whose lists name it. An attribute the target defines but a class does not allow (an auxiliary class the target lacks) fails at the first object with an object class violation, with the server's message. The Samba lab has Windows' base schema and no product's: a lab image built with `make image EXCHANGE_ISO=<Exchange setup image>` gives every lab Exchange's (what `/PrepareSchema` writes, when the lab's domain is created; the image holds Microsoft's files, so it stays on your machine), and `ldap-cronin schema` gives it the others before the first `clone` (it prints what the target lacks as LDIF; `-apply` writes it), and the snapshots taken after carry them. The [tutorial](tutorial-ad.md#attributes-of-your-own-schema-extensions) goes through it step by step.
- **`ldap-cronin schema`** compares the `attributeSchema` and `classSchema` entries of the two schema naming contexts by `lDAPDisplayName` and plans what the target lacks: the attributes, then the classes (after the class each derives from), then the values of the classes both have (`mayContain`, `auxiliaryClass`, `possSuperiors`, so `user` gets your auxiliary class), with a `schemaUpdateNow` after each step. A back link (odd `linkID`) is added after its forward link, whatever their names: Windows refuses it before (53, data 8482); one whose forward link neither schema has is left out with why. The definitions keep the source's OIDs, `schemaIDGUID`, `linkID` and the rest a client sets; DNs move to the target's schema naming context. Left out, each with why: definitions of a newer Windows Server base schema than the target's (`systemFlags` 0x10; the lab's level is chosen when it is provisioned), a name or OID the target uses for something else, a `mustContain` a class the target has cannot be given, and what depends on those. Without `-apply` it writes nothing. A schema change cannot be undone in AD, so for a test AD write the file, review it and apply it as a member of Schema Admins, against the schema master (`-apply` with `[target] url` on the schema master does the same; another DC refuses the change).
- **DN-valued attributes** are found in the source schema (`attributeSyntax=2.5.5.1`), so an attribute added with `extra_include` is handled too. So are the other syntaxes that hold a DN. `2.5.5.7` is two of them, told apart by `oMObjectClass`: Object(OR-Name), whose LDAP value is the DN alone (Exchange's delivery restrictions of a recipient: `authOrig`, `unauthOrig`, `dLMemSubmitPerms`, `dLMemRejectPerms`, who may or may not send to it), and Object(DN-Binary), `B:<count>:<hex>:<DN>`; `2.5.5.14` is DN-String, `S:<count>:<string>:<DN>` (Exchange's supervision lists, `msExchSupervision*Link`). The form of each value tells which it is. Their DN is a reference like a member (an object outside the scope is cloned, a dump carries it, `diff` compares it and translates a rename), and the binary or string part is written as the source has it. `B:0::<DN>` and `<DN>` compare equal, whichever form a server returns. A well-known principal inside such a value is skipped with its reason (its SID form there is not known to be taken). Credentials of that syntax (`msDS-KeyCredentialLink`, `msPKI-CredentialRoamingTokens`, ...) are cloned only with `[attributes] credentials = "copy"`, and a warning about one prints its DN alone. `member` is always read in explicit ranges, as AD splits large groups ([operations.md](operations.md#large-data-sets)).
- **Comparison** normalizes `userAccountControl` (server-managed bits) and `accountExpires` (`0` and `9223372036854775807` both mean "never"); see [diff.md](diff.md#what-is-compared).
- **What the target refuses.** An attribute the target's schema marks `systemOnly` is written by the server alone, though the source's schema may let a client write it. The resource-based delegation (`msDS-AllowedToActOnBehalfOfOtherIdentity`) is the exception: both Windows' schema and Samba's mark it `systemOnly`, yet Windows lets a client write it (measured on Windows Server 2019), so it counts as a client's from either source and is written into Windows; Samba 4.19.5 holds a client to it ("can only be modified as system"), so it is left out there. Samba will also not have `userParameters` written over LDAP ([bug 8077](https://bugzilla.samba.org/show_bug.cgi?id=8077); Windows takes it), told from Windows by the target's root DSE (`vendorName`, which Windows does not publish). `clone` and `diff` leave them out, in any mode, and name each with the reason; `check` notes them. A native import writes as the system and takes them all. A dry-run does not connect to the target, so its LDIF still carries it.
- **Rename and move detection.** AD refuses a client-set `objectGUID` over LDAP, so `clone` writes a marker of the source object into `adminDisplayName` (`ldap-cronin:<source root>:<source key>`); how `diff` uses it is in [diff.md](diff.md#how-rename-and-move-detection-works-and-its-configuration). `[target.lab] native = true` keeps the `objectGUID` itself, but only into the Samba lab ([lab.md](lab.md#importing-with-the-same-objectguid-and-objectsid-targetlab-native--true-samba-only)).

## When the target is a real AD

- Setting a user's password (`unicodePwd`) **requires LDAPS**. Over `ldap://` the password change is rejected (Samba does the same).
- The fixed password must satisfy the target domain's password policy (complexity and so on). Otherwise setting the password after creating the user fails, and the user stays disabled.
- The LDAP signing policy may reject a simple bind over `ldap://`. Use LDAPS or `start_tls`.
- For a self-signed or internal certificate, pass the CA with `ca_file`. For testing only, `insecure_skip_verify` is also available.
- **Index the marker attribute** before the first `clone`: set bit 1 in the `searchFlags` of its `attributeSchema` entry (`CN=Admin-Display-Name,CN=Schema,CN=Configuration,...` for `adminDisplayName`). Without it `clone` warns, and every search for a moved object reads the whole naming context. The lab image does this by itself.
- Writes are replicated to the other DCs. Run against a test domain, outside business hours; the load per user is in [operations.md](operations.md#load-on-the-target-ad-clone).

## Limitations

- Only the [kinds](../README.md#kinds) are cloned: OUs, groups, users, computers and contacts (`list-attrs` shows how each is told). Other object classes (BitLocker recovery information, password settings objects, managed service accounts, GPOs) are reachable only through custom per-kind `[scope.filters]` and `[attributes]`; a member of such a class is skipped with a warning and counted by `diff`. A managed service account derives from `computer` but is no `computer`: a group holding one does not bring it in as one.
- Verified on Windows Server 2019 (a test forest on EC2, with the e2e tests run in both directions against Samba, as the Administrator):
  - the clone, a second run that writes nothing, the fixed password over LDAPS, diff;
  - adding a computer with `userAccountControl` 4130 and then setting 4096;
  - a member naming a built-in group by DN (Domain Admins), and members added to a built-in group (Account Operators);
  - the search for the groups holding entries (`(memberOf=*)`; `*` returns `memberOf`);
  - the primary group sequence: the member added, `primaryGroupID` set to the target's RID, the member value then dropped by the DC;
  - `pwdLastSet=0` right after the password, also when `userAccountControl` (set after it) has "password never expires";
  - `schema -apply` from a Samba lab with Exchange's schema (Exchange Server SE): 2,445 attributes, 314 classes and 20 classes extended, all taken, in about 4 minutes (about 12 definitions a second through an SSM tunnel); a back link had to follow its forward link;
  - DN-Binary values: Windows takes and returns `B:0::<DN>` and `B:<count>:<hex>:<DN>` as written, as Samba does (a linked attribute of that syntax made for the test);
  - `authOrig` and `dLMemSubmitPerms` (Object(OR-Name)) cloned from a Samba lab with Exchange's schema, with the sender outside the scope created, and diff clean: both servers take and return the DN alone, and refuse a `B:0::` form (Samba 34, Windows 19);
  - a must-change user's re-run setting the same password again under a password history of 24 (an administrator's reset is not checked against the history).
- Not yet verified on a real AD:
  - writing the marker, or adding members to a built-in group, with a delegated (non-admin) account;
  - interference with the marker attribute by Exchange, Entra Connect or ADUC's "copy user";
  - the groups holding entries, the primary group and `pwdLastSet=0` through `[target.lab] native = true` (they go through the same steps; not in its test);
  - the groups holding entries of a generic LDAP source through OpenLDAP's memberof overlay (the code reads its `memberOf`; not in a test);
